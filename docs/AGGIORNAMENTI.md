# Aggiornamenti: come si pubblica una versione e come la riceve un'installazione

Il sistema di aggiornamento è modellato su quello di [Pinakes](https://github.com/fabiodalez-dev/Pinakes) (`app/Support/Updater.php`, `docs/CREATING_UPDATES.md`), adattato a Laravel. Questo documento è l'equivalente di `CREATING_UPDATES.md`.

## Le parti

| Pezzo | Dove | Cosa fa |
|---|---|---|
| Versione installata | `VERSION` | Un numero semver per riga. Lo legge `config('update.version')` e lo sovrascrive il pacchetto. |
| Pacchetto | `bin/build-release.sh` | Costruisce `releases/gestionale-associazioni-vX.Y.Z.zip`: una cartella `gestionale-associazioni/` con l'app completa (`vendor/` di produzione, `public/build`, cartelle di runtime, `.htaccess` di protezione, nessun `.env`). |
| Pubblicazione | `.github/workflows/release.yml`, `bin/create-release.sh` | Al tag `v*` la Action costruisce il pacchetto con PHP 8.4, controlla che `VERSION` coincida con il tag e carica zip e `.sha256` nella GitHub Release. Lo script locale fa i controlli, crea il tag, attende la Action e verifica gli asset. |
| Updater | `app/Services/Update/UpdateService.php` | Controllo release, preflight, backup, download verificato, copia, migration, rollback. |
| Interfaccia | `/aggiornamenti` (super admin), `php artisan app:aggiorna` | Pagina con stato, requisiti, pulsante di aggiornamento, upload del pacchetto, backup, storico; comando CLI con lo stesso flusso. |
| Schema per nuove installazioni | `database/installer/schema.sql`, `php artisan installer:genera-schema` | Dump del database vuoto che l'installer web inietta. |

## Cosa fa l'updater, passo per passo

1. **Lock** esclusivo su `storage/framework/aggiornamento.lock` (flock): mai due aggiornamenti insieme. `ignore_user_abort`, nessun limite di tempo, memoria almeno 256 MB.
2. **Preflight**: PHP ≥ 8.4, estensione zip, radice/`app`/`vendor`/`public`/`bootstrap/cache`/`storage` scrivibili, spazio libero ≥ 200 MB, prova di scrittura reale (1 MB in `storage/app/updates`, perché `disk_free_space` non vede la quota dell'account su cPanel).
3. **Backup del database**: `php artisan backup:run --only-db` (spatie/laravel-backup, usa `mysqldump`); se non è disponibile, dump in PHP puro (`DumpDatabasePhp`, struttura + dati, gzip) in `storage/app/private/aggiornamenti/`. Senza backup non si aggiorna.
4. **Pacchetto**: dalla release GitHub del tag richiesto si prende l'asset `gestionale-associazioni-vX.Y.Z.zip` e il suo **digest sha256 dall'API GitHub** (campo `digest`, servito via TLS da `api.github.com`). Il download va direttamente su file, lo sha256 del file deve coincidere, altrimenti rifiuto. Niente digest = niente aggiornamento (il `.sha256` pubblicato a fianco serve a chi scarica a mano: arriva dallo stesso CDN e non proverebbe nulla). Nessun ripiego sullo zipball dei sorgenti, che non contiene `vendor/`. In alternativa, un pacchetto caricato dall'utente (pagina) o indicato da CLI: stesso flusso, senza verifica del digest.
5. **Estrazione** in `storage/app/updates/extract_*` con controllo anti zip-slip; la radice del pacchetto deve contenere `artisan`, `VERSION`, `vendor/autoload.php`, `public/index.php`, `bootstrap/app.php`; la versione nel pacchetto deve essere quella richiesta.
6. **Prova a secco**: ogni destinazione che il processo PHP non potrebbe scrivere viene elencata (con tentativo di `chmod u+w` dove il proprietario coincide) e l'aggiornamento si ferma prima di toccare un byte, suggerendo `php artisan app:aggiorna` da terminale (gira come proprietario dei file). Spazio richiesto: due volte il pacchetto estratto più 50 MB.
7. **Manutenzione** (`artisan down`), **backup dei file** che verranno sovrascritti in `storage/app/updates/filebackup_*`, **copia** del pacchetto sulla radice saltando i percorsi preservati (`config('update.preserve_paths')`: `.env`, `storage`, `public/storage`, `public/uploads`…: un file nuovo del pacchetto dentro un percorso preservato viene aggiunto, uno esistente non viene toccato), **pulizia degli orfani** nelle cartelle di codice (`config('update.orphan_dirs')`: `app`, `config`, `database`, `resources`, `routes`, `vendor`, `public/assets`, `public/build`, `bin`, `lang`).
8. **Post-installazione** in un processo PHP separato (`php artisan …` con il binario corrente), perché il processo che ha copiato i file ha ancora in memoria il kernel e le classi della versione vecchia: cancellazione delle cache di bootstrap (config, rotte, eventi; `packages.php` e `services.php` arrivano freschi dal pacchetto), `optimize:clear`, `migrate --force`, `app:aggiorna-permessi`, `queue:restart`, `storage:link` se manca. Poi `artisan up`.
9. **Esito** in `update_logs` (`completato`, `fallito`, `rollback`). Se qualcosa fallisce dopo l'inizio della copia, i file tornano com'erano dal backup e il messaggio ricorda che il database (migration già eseguite) va eventualmente ripristinato dal backup del passo 3; se anche il ripristino dei file fallisce, **il sito resta in manutenzione** e il messaggio indica la cartella `filebackup_*` da rimettere a mano. Un errore fatale a metà copia (limite di tempo, memoria) passa dalla funzione di shutdown, che tenta lo stesso rollback con la stessa regola. Una manutenzione rimasta accesa da più di 30 minuti senza aggiornamento in corso si sblocca dalla pagina, ma solo dopo aver controllato lo storico.

Un pacchetto caricato a mano con una versione più vecchia di quella installata viene rifiutato: le migration non sono reversibili, per tornare indietro si ripristina un backup.

La pagina lancia l'aggiornamento via fetch e nel frattempo interroga `/aggiornamenti/stato` ogni 3 secondi: se un proxy chiude la connessione prima della fine, l'esito arriva comunque dal polling.

## Pubblicare una versione

1. Codice pronto sul branch, test verdi.
2. Se ci sono migration nuove: `php artisan installer:genera-schema` (il test `SchemaSqlTest` fallisce altrimenti).
3. Aggiorna `VERSION` (semver; con `-rc.N` è una prerelease, visibile solo alle installazioni con `UPDATE_CHANNEL=rc`).
4. Commit e push.
5. `bash bin/create-release.sh X.Y.Z`: controlla tree pulito, `VERSION`, schema allineato; crea e pusha il tag; aspetta la Action; verifica che la release abbia zip, `.sha256` e digest API coerenti.

Le note di rilascio le genera GitHub dai commit (`--generate-notes`); si possono riscrivere dalla pagina della release, la pagina `/aggiornamenti` le mostra.

## Migration e dati

Le migration sono quelle di Laravel (`database/migrations`), idempotenti per costruzione (ogni file gira una volta, registrato in `migrations`). Il pacchetto non porta file SQL per versione come Pinakes: lo stesso risultato lo dà `migrate --force` in post-installazione. Lo schema SQL serve solo alle installazioni nuove e deve restare allineato (`installer:genera-schema`).

Regole:
- mai modificare una migration già rilasciata: se ne aggiunge una nuova;
- una migration che tocca molti dati va provata su una copia del database di produzione;
- se una migration fallisce, l'updater fa il rollback dei file ma **non** del database: si ripristina il backup del passo 3 (`storage/app/private/<nome app>/*.zip` di spatie o il `.sql.gz` dell'updater), si corregge e si riprova.

## Note per chi aggiorna da una versione precedente alle correzioni di sicurezza

Le correzioni dell'audit di sicurezza (branch `fix/security-audit-run-1`) sono pensate per non interrompere le installazioni esistenti. Cosa cambia in pratica:

- **Chiavi API legacy**: la migration converte le chiavi in chiaro in hash (`api_key_hash`) e conserva un prefisso per riconoscerle; le chiavi già distribuite continuano a funzionare. La chiave in chiaro non è più recuperabile dal pannello: chi l'ha persa ne genera una nuova. `app:import-legacy` hasha le chiavi del gestionale precedente durante l'import.
- **Token Sanctum**: i token nuovi scadono dopo 365 giorni (o prima, se indicato); quelli esistenti senza scadenza ricevono dalla migration un anno di validità dall'aggiornamento. `SANCTUM_TOKEN_EXPIRATION` (minuti) regola il limite per eventuali token ancora senza scadenza.
- **Inviti amministratore**: i link inviati prima dell'aggiornamento (senza nonce) restano accettati una sola volta, solo se l'invitato non ha mai effettuato un accesso e al massimo per 7 giorni dalla creazione dell'account; dopo il primo uso, il primo login o un reinvio valgono solo i link nuovi.
- **Verifica tessere**: il QR deve contenere l'URL firmato (lo è da sempre per le tessere emesse da questa applicazione). Le tessere importate con `qr_code_url` legacy senza firma restano verificabili con il solo UUID (eccezione limitata a quelle righe, che solo l'import o l'emissione possono scrivere). Ogni ristampa (singola o massiva) usa già l'URL firmato; una volta ristampate, `php artisan tessere:firma-qr` riscrive i loro URL e chiude l'eccezione (`--dry-run` per contarle).
- **PayPal**: il Webhook ID è obbligatorio. Le associazioni che hanno PayPal abilitato senza Webhook ID vedono un avviso nelle impostazioni pagamenti e PayPal non viene proposto ai paganti finché il campo non è compilato.
- **CORS**: l'API non emette più `Access-Control-Allow-Origin: *`. Un'integrazione da browser su un'altra origine va dichiarata in `CORS_ALLOWED_ORIGINS`.
- **SMTP dei tenant**: l'host configurato da un'associazione deve essere un server di posta pubblico, controllato a ogni invio (e la connessione va all'IP appena validato). Chi usa un relay locale o in rete privata (es. il Postfix dell'hosting) lo dichiara una volta per tutta la piattaforma in `SMTP_TENANT_HOST_PRIVATI` (es. `localhost,127.0.0.1`, oppure `host:porta`; senza porta valgono solo 25, 465, 587 e 2525); fino ad allora le notifiche di quell'associazione partono dal mailer di default e il log lo segnala.
- **Area soci**: soci in attesa di approvazione e soci cessati non accedono più al portale; soci sospesi o in attesa di pagamento sì.
- **Utenti staff senza associazione**: non vedono più la vista globale; chi è stato rimosso da un'associazione resta disattivato finché non viene ricollegato.
- **Link di pagamento**: dopo il pagamento il link resta valido un'ora per la ricevuta; poi la ricevuta si scarica dall'area riservata.
- **Seeder**: `php artisan migrate --seed` in produzione crea solo ruoli e permessi.
- **2FA del super admin**: un super admin senza autenticazione a due fattori confermata, dopo il login, viene portato alla pagina profilo e non può usare le altre pagine finché non la attiva (servono un'app di autenticazione e la password, nulla da fare da terminale). L'aggiornamento in corso, l'installer e le API non sono toccati, e gli altri ruoli restano come prima. Chi perde il telefono rientra con `php artisan admin:recupera-accesso <email> --azzera-2fa`; `SUPER_ADMIN_2FA_OBBLIGATORIA=false` nel `.env` riporta la 2FA a facoltativa.
- **Content Security Policy**: gli script inline delle pagine sono ora autorizzati da un nonce generato a ogni richiesta e `script-src` non contiene più `'unsafe-inline'` né i CDN jsdelivr/cdnjs (tutte le librerie sono già servite da `public/assets/vendor`). Le conferme e le altre azioni che erano scritte come `onclick`/`onsubmit`/`onchange` nelle pagine ora usano attributi `data-*` gestiti da `assets/js/azioni-dichiarative.js`. Chi ha aggiunto view personalizzate con script o handler inline deve marcare gli script con `@cspNonce` (e spostare gli handler in un listener); in alternativa `CSP_NONCE_ENABLED=false` nel `.env` ripristina la policy precedente con `'unsafe-inline'`. Gli stili inline restano ammessi.
- **Stessa email in più associazioni (area soci)**: prima il login e il link "imposta password" prendevano un solo socio a caso tra quelli con quell'email, e l'altra iscrizione restava irraggiungibile. Ora la password viene verificata su tutte le iscrizioni: se combacia con una sola si entra lì, se combacia con più di una (stessa password) la pagina di login chiede in quale associazione entrare. La richiesta del link invia un'email per ciascuna associazione, ognuna con il proprio link e il nome dell'associazione nell'oggetto. Nessuna azione richiesta.
- **Backup cifrati**: gli zip di backup contengono anche il `.env` (serve al ripristino). Le installazioni nuove ricevono dal wizard una password casuale in `BACKUP_ARCHIVE_PASSWORD`, mostrata una volta nella pagina finale. Sulle installazioni esistenti senza password la pagina Impostazioni di sistema mostra un avviso e, in "Backup e aggiornamenti", l'opzione "Genera una password casuale" (mostrata una volta dopo il salvataggio). La password vale per i backup creati da quel momento: quelli già esistenti restano non cifrati e apribili come prima. Conservala fuori dal server: senza non si aprono gli archivi per un ripristino.
- **API REST /api/v1 senza sessione**: le rotte `/api/v1/*` (eventi compresi) passano ora per il gruppo `api` invece che per quello web: stessi URL, stessi nomi di rotta, stessi codici di risposta e stessa autenticazione (chiave API o token Sanctum), ma le risposte non creano più una sessione e non impostano cookie (`XSRF-TOKEN`, cookie di sessione). Un client che per errore si appoggiava a quei cookie non ne aveva bisogno: l'API non li ha mai letti. Con l'applicazione non ancora installata l'API risponde `503` con `code: not_installed` invece di un redirect HTML a `/install`. Le pagine `/api-keys`, `/api-tokens`, `/api-docs` e `/checkin` restano pagine web come prima. Chi ha personalizzato le rotte dei moduli trova le definizioni API in `routes/modules/api/`.
- **Revoca dei token API da parte degli amministratori**: la nuova pagina `/api-tokens` (link "Token degli utenti" nella pagina Chiavi API) elenca i token personali Sanctum degli altri utenti e permette di revocarli: il super admin vede quelli di tutti, l'admin di un'associazione quelli degli utenti della propria associazione (mai quelli dei super admin né di altre associazioni). Ognuno continua a revocare i propri token dalla pagina Chiavi API; un tentativo di revocare un token altrui senza permesso ora riceve un `403` invece di un redirect silenzioso.
- **Assemblee, elezioni e allegati**: chi proclama un'elezione con il solo permesso sulle riunioni (segretario, presidente, vicepresidente) la porta ancora a "proclamata" e registra gli eletti, ma la chiusura delle cariche uscenti e la creazione delle nuove nel registro degli organi sociali restano da confermare: gli amministratori dell'associazione ricevono un avviso e confermano con il pulsante "Conferma le cariche" nella pagina dell'elezione (se proclama un amministratore, tutto avviene subito come prima; le elezioni già proclamate restano come sono). Una riunione con eletti proclamati o votazioni concluse non si elimina più (si può impostare come annullata); le presenze non si modificano su riunioni annullate, su assemblee già svolte o dopo votazioni concluse (nelle riunioni del direttivo svolte si registrano ancora finché non ci sono votazioni); conflitti di interesse non si aggiungono né si tolgono su un punto con il voto online già aperto o chiuso; le deleghe contano solo se l'assemblea le ammette; il codice della tessera non identifica più soci cestinati o cessati. Immagini (galleria, foto socio, logo) al massimo 8000×8000 pixel; galleria e allegati salvati su disco con un nome casuale (il nome originale resta come etichetta e nome del download); gli allegati fino a 20 MB ora si caricano davvero (nuovo `config/media-library.php`, identico a quello del pacchetto salvo `max_file_size`); l'import Excel dei soci sceglie il formato dal contenuto del file.
- **Chiavi API globali esplicite**: una chiave API è globale (accesso a tutte le associazioni) solo se creata come tale da un super admin; prima bastava che non avesse un'associazione, e le chiavi di un'associazione eliminata diventavano globali. La migration marca come globali tutte le chiavi esistenti senza associazione, così quelle create apposta continuano a funzionare, e da ora eliminare un'associazione cancella le sue chiavi API e revoca i token personali dei suoi utenti (anche rimuovere un amministratore ne revoca i token). Le chiavi di associazioni eliminate in passato non sono distinguibili dalle globali vere: dopo l'aggiornamento il super admin deve aprire la pagina Chiavi API (senza associazione selezionata), controllare le chiavi con il badge "Globale" ed eliminare quelle che non riconosce. Un amministratore ricollegato a un'associazione dopo essere stato rimosso resta disattivato: la pagina avvisa e lo si riattiva dalla pagina Amministratori.
- **CSS di template email e annunci**: i blocchi `<style>` salvati dall'editor non passano più da una lista di parole vietate ma vengono ricostruiti regola per regola: restano selettori semplici, `@media` e le proprietà di layout, colori e tipografia (quelle prodotte da GrapesJS e dal preset newsletter); spariscono `url()`, `@import`, `@font-face`, `expression()`, `behavior`, `-moz-binding`, la proprietà `content`, `position` diversa da `static`/`relative` e i valori con escape. Vale per i salvataggi da ora in poi: template e annunci già salvati restano come sono finché non vengono modificati; un'immagine di sfondo messa via CSS va spostata in un tag `<img>`. Nessuna azione richiesta.
- **Iscrizione di un'associazione alla piattaforma (`/registrati`)**: il modulo non risponde più "esiste già un account con questa email" né "codice fiscale/partita IVA già iscritti". Se l'email dell'amministratore è già di un utente (o di una richiesta confermata in attesa) la pagina è la stessa di un invio riuscito, la richiesta non viene creata e il titolare dell'indirizzo riceve un'email con il link per accedere o recuperare la password. Con email, codice fiscale o partita IVA dell'associazione già presenti la richiesta segue il percorso normale: dopo la conferma dell'email arriva al super admin (anche in modalità automatica), che all'approvazione vede l'avviso di doppione come già accadeva. Nessuna azione richiesta.
- **Registrazione sul mini-sito (`/a/{slug}/registrati`)**: con un'email già registrata nell'associazione la risposta è identica a quella di una registrazione nuova e il titolare riceve un'email con il link al recupero password (al massimo 3 al giorno); nessun account duplicato. Dopo la registrazione non si entra più automaticamente: si torna alla pagina di accesso con l'invito a confermare l'email, poi si accede con email e password (l'accesso funziona anche prima della conferma, come prima). Gli account esistenti non cambiano.
- **Iscrizione socio da ospite (`/a/{slug}/iscriviti` senza account)**: la richiesta non crea più subito un socio "In Attesa". I dati restano in sospeso (cifrati, nuova tabella `iscrizioni_da_confermare`, creata dalla migration) e il richiedente riceve un'email con un link valido 48 ore: solo al clic nascono socio e richiesta, partono l'avviso alla segreteria e il riepilogo al richiedente. Vale anche per la modalità "diretta". Le richieste non confermate non occupano l'email e vengono eliminate alla scadenza (al primo invio successivo o con `php artisan model:prune --model="App\Models\IscrizioneDaConfermare"`). Da ospite, un'email già di un socio o con una richiesta in attesa riceve la stessa risposta di un invio riuscito, senza email. Richieste e soci "In Attesa" già presenti restano come sono; il flusso con account loggato non cambia. Serve che l'invio delle email funzioni (come per la verifica degli account).

## Dove guardare quando qualcosa va storto

- Storico nella pagina `/aggiornamenti` (`update_logs`: versione, esito, messaggio d'errore).
- `storage/logs/laravel.log` (voci `UpdateService:`).
- File lasciati in `storage/app/updates/` dopo un rollback fallito: `filebackup_*` contiene i file precedenti, `.voci.json` dice cosa ripristinare.
- Manutenzione accesa senza aggiornamento in corso: pulsante "Togli la manutenzione" nella pagina, oppure `php artisan up`.
- Hosting dove PHP del web server non può scrivere i file: `php artisan app:aggiorna --versione=X.Y.Z` da terminale (o `--pacchetto=/percorso/zip`), che gira come proprietario dei file. `UPDATE_SELF_ENABLED=false` nasconde il pulsante dalla pagina.
- API GitHub oltre il limite (60 richieste/ora senza token): salva un token dalla pagina (finisce in `.env` come `UPDATE_GITHUB_TOKEN`).

## Differenze rispetto a Pinakes

- Migration Laravel al posto dei file `migrate_X.Y.Z.sql`; nessun patch pre/post-update scaricato dalla release.
- Manutenzione con `artisan down`/`up` invece del file `storage/.maintenance`.
- Backup del database con spatie/laravel-backup quando c'è `mysqldump`, altrimenti dump PHP come Pinakes.
- Token GitHub nel `.env` invece che cifrato nel database.
